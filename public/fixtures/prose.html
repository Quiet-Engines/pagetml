On the Pagination of Arbitrary Documents

Browsers are the most dynamic rendering engines in existence, yet no mainstream tool presents an arbitrary HTML document as discrete, navigable pages the way a PDF reader or a slide deck does. The gap is pagination and presenting, not rendering.

Correctly rendering HTML and CSS means using a real engine. A standalone reader is realistically a desktop app that embeds a web engine and adds the pagination and presenter experience on top. The product value is that experience, not a new engine.

The multi-column technique

The body is wrapped in a container whose column width equals the viewport width and whose height is fixed, so the engine itself flows content into fixed-size columns; each column is one page. Page turns translate the container horizontally by whole page widths.

The browser's own line-breaking, float, and fragmentation logic does the heavy lifting, which is the only realistic way to correctly paginate arbitrary HTML. Break properties flow through natively via column fragmentation.

Measuring element rectangles while a transform transition is mid-flight returns interpolated values; subtract the flow's current transform from every measurement so the animation cancels out exactly.

Position anchors are a path to the first visible element plus a character offset, surviving repagination and restarts. After shrinking the window the anchor heading legitimately moves to an earlier page because more content fits per page; tests must assert on containment, not on expected page numbers.

Hostile content

Elements taller than one page — large images, tall tables, preformatted blocks — need explicit handling: scale images to fit, fragment tables and code where possible, mark the page internally scrollable as a last resort.

Fixed and sticky elements are normalized to absolute within the page because they are inconsistent inside columns across engines. Documents with a single top-level full-height scroll container are unwrapped into flowed content when detected.

A corpus covering the hard cases plus real-world exports — word-processor HTML, Pandoc output, notebook conversions, single-file builds — guards the behavioral contract. Assertions are on invariants, never on exact page counts.

The known tension is that with auto-fit, page seven on the laptop may not be page seven on the projector. Locking at fullscreen entry means the app repaginates once at the display's resolution, then freezes boundaries for the duration of the presentation.

Under auto-fit, differing page counts across engines and window sizes are acceptable and expected. Engines must agree on behavior, not pixel-identical boundaries; the fixture suite guards that contract on both Chromium and WebKit.

The chrome should recede completely around the content: a dark theater, a lit stage, and a single spotlight-amber accent carrying the interactive elements. Reading mode shows only a slim status bar; presentation mode shows no chrome at all.
